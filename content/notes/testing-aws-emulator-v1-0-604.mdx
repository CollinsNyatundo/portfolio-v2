Most local test suites for AWS apps mock `boto3`. Those tests check that your code called a method with the arguments you expected; they don't check that AWS would accept the request, enforce the policy, or respect the resource lifecycle. When [`aws/aws-emulator`](https://github.com/aws/aws-emulator) shipped `v1.0.604` (commit `bca2a3c474`, 436 service crates in Rust), I wanted to see what actually works against real SDK and Terraform traffic at $0, and where it breaks.

I tested it two ways on Docker Desktop 29.9.3 (Windows 11, official Amazon Linux 2023 RPM container, telemetry off, 2 GiB memory limit):

1. I wired an optional 7-service AWS profile into [the Production AI Reference Template](/work/production-ai-template) (`S3`, `S3 Vectors`, `KMS`, `Secrets Manager`, `SQS` with a dead-letter queue, `DynamoDB`, and `CloudWatch` with `X-Ray`) and ran a live, zero-mock `pytest` suite against port `9297`.
2. I pointed Terraform 1.9 (`hashicorp/aws v5.100.0`) at the same container in a private local harness against an anonymized 10-service infrastructure stack (`VPC`, subnets, security groups, `KMS`, `IAM`, `CloudWatch Logs`, `S3`, `EKS`, `RDS`, `MSK` and `ElastiCache`) backed by an S3 state bucket and a DynamoDB lock table.

## The numbers before the caveats

In `v1.0.604`'s published evaluation suite (`scores.json.gz`, 46,037 units scored on 2026-11-24), the overall pass rate is 80.0% (36,841 of 46,037 units): 81.0% across 38,808 single-service checks and 74.6% across 7,229 cross-service scenarios. Locally, the container started and generated its TLS CA and SigV4 credentials in 1.0 s. At peak during the private local Terraform run, serving 23 Terraform-managed resources alongside S3 remote state and a DynamoDB lock table, it used 202.3 MiB of RAM and 0.01% CPU.

The core application services were fast and strict with `boto3 1.44.10`:

- **Amazon S3 Vectors (`s3vectors`)**: creating a vector bucket and cosine index, writing vectors, and running a `topK` query took a measured 39.7 ms combined latency (not query latency alone) and returned the expected neighbour distance and tenant metadata.
- **KMS tenant isolation**: encrypting tenant A's text with `EncryptionContext={"tenant_id": "tenant-alpha"}` and attempting to decrypt it under `"tenant-beta"` failed with `InvalidCiphertextException`, matching AWS.
- **S3 with SSE-KMS and versioning**: `PutObject`, `HeadObject`, and `GetObject` all returned the full KMS key ARN in `SSEKMSKeyId` and a `VersionId`.
- **SQS dead-letter redrive**: leaving a message unacknowledged past a 1-second visibility timeout with `maxReceiveCount=1` moved it cleanly to the dead-letter queue.

## Where it caught real mistakes mocks hide

Three things failed on my first run not because the emulator was broken, but because my first pass was looser than AWS:

1. **Missing SQS resource policies.** Both `SNS -> SQS` fan-out and `EventBridge -> SQS` rule delivery silently dropped messages until I attached least-privilege SQS queue policies granting `sns.amazonaws.com` and `events.amazonaws.com` `sqs:SendMessage` scoped to `aws:SourceArn`. Once attached, messages arrived in 35 ms and 43 ms.
2. **DynamoDB table lifecycle.** Calling `PutItem` right after `CreateTable` failed with `ResourceNotFoundException` because the table starts in `CREATING`. Adding `get_waiter("table_exists").wait(...)` fixed it.
3. **Deprecated service versions in Terraform.** Applying older pins from an existing config failed immediately against the emulator's 2026 service catalogues: EKS `1.28` returned `InvalidParameterException`, RDS PostgreSQL `15.4` returned `InvalidParameterCombination`, and MSK Kafka `3.5.1` returned `BadRequestException`. Updating to current catalogue versions (`EKS 1.37` and `RDS PostgreSQL 18.3`) provisioned cleanly to `ACTIVE` in 15.9 s and 94.9 s with zero drift on re-plan.

## Four real gaps and traps in `v1.0.604`

1. **Docker Compose TLS hostname mismatch.** Inspecting the live X.509 certificate on port `9297` showed `rcgen` issues SANs only for `localhost`, `127.0.0.1`, and `::1`, and `aws-emulator --help` has no flag to add a custom SAN. A sibling container calling `https://aws-emulator:9297` fails strict TLS verification. Sharing the emulator's network namespace (`network_mode: "service:aws-emulator"`) lets the app talk to `https://127.0.0.1:9297` with strict `AWS_CA_BUNDLE` checks intact.
2. **ElastiCache ephemeral port causes ForceNew Terraform drift.** Requesting `port = 6379` on `aws_elasticache_cluster` succeeded after 30 s, but the emulator bound an ephemeral loopback port (`127.0.167.91:42843`) and reported `42843` back to Terraform. Because `port` is `ForceNew` in `hashicorp/aws`, an immediate `terraform plan -detailed-exitcode` returned exit code `2` and planned a destroy-and-recreate cycle. Every other created resource (22 of 23) showed zero drift.
3. **MSK version catalogue disagrees with its own validator.** `kafka:ListKafkaVersions` returned `4.2.x.kraft` twice at the end of the list, yet `kafka:CreateCluster` rejected `4.2.x.kraft` for standard `kafka.m5.xlarge` brokers with `Valid values: [3.8.x, 3.8.x.kraft, 3.9.x, 3.9.x.kraft, 4.0.x.kraft, 4.1.x.kraft]`.
4. **Control plane is not data plane.** The emulator validates RDS, ElastiCache, MSK, and SageMaker control-plane calls, and its `scores.json.gz` open issues confirm that services like SageMaker training jobs do not execute workloads and CloudFormation remains at 18.8% single-service pass rate (600 open issues). Keep real Postgres or Redis containers for data-plane queries, and use the emulator for AWS APIs.

## What this doesn't cover

- Every measurement here is from a single local container on Windows Docker Desktop against `v1.0.604`; newer releases land daily and may close the ElastiCache and MSK mismatches.
- The 7-service RAG integration tests use a deterministic 64-dimensional hashing embedder so CI needs no external embedding key; they verify S3 Vectors API wiring and tenant isolation, not retrieval quality.
- AWS Emulator is explicitly not for testing real IAM security boundaries or running production workloads.

## What I do now

- Run zero-mock integration tests for `S3`, `S3 Vectors`, `KMS`, `Secrets Manager`, `SQS`, `DynamoDB`, and `CloudWatch`/`X-Ray` in CI against `aws-emulator`, instead of mocking `boto3`.
- Keep `network_mode: "service:aws-emulator"` in Compose overlays so `ca.pem` stays verified without disabling TLS checks.
- Pin `lifecycle { ignore_changes = [port] }` only in local Terraform test overrides when exercising ElastiCache, and check `scores.json.gz` before trusting a service's fidelity.
