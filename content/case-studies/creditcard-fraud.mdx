## Problem

Card fraud is rare and expensive. In this dataset it's 0.17% of payments, so a model that calls everything legitimate is 99.8% accurate and useless. The job is to catch as much fraud as possible, with few enough false alarms that someone will still read them, quickly enough to decide before the payment clears.

## Constraints

- **Time.** A score has to come back within the 10 ms the project set for itself, so a slower configuration loses even if it's more accurate.
- **No peeking at the future.** Fraud patterns change over time. Training on a random shuffle would let the model learn from transactions that happen after the ones it's tested on.
- **Few positives.** 284,807 transactions hold only 492 frauds, so every metric on the test set rests on a few dozen cases.

## Approach

<Figure caption="One transaction's path through the model. The window features are why a single row can't be scored on its own.">
  <FraudPipeline />
</Figure>

I split the data by time, 70/15/15: training on the earliest transactions, tuning and calibrating on the next block, and holding out the last 42,722 for the final test. The published run did not fit every statistic on the training block alone; the first limit below says what that changed.

Beyond the 28 PCA components and the amount, the model sees 50 engineered features. Most describe how a transaction compares with the transactions just before it in time. The dataset has no card identifier, so these windows run over the whole time-ordered stream, not one card's history: rolling means, spreads and z-scores of the amount over the previous 3, 5 and 10 transactions, the time since the last one, and cumulative spending.

The model is LightGBM trained with focal loss, which concentrates learning on hard, rare examples. SMOTE plus undersampling rebalanced the training block. Optuna searched the hyperparameters and threw out any configuration too slow to serve. Platt scaling (a logistic regression on the model's score, fitted on the validation block) made the probabilities usable as probabilities.

## Evaluation

Every number below comes from the time-ordered holdout, which the model never saw during training or tuning. The decision threshold is the one stored in the repository with the model.

<Metrics />

Bootstrap resampling of the holdout gives the intervals in the caveats. They're wide because the holdout holds few frauds, and they're the honest reading of the result.

## Results

The model catches three in four frauds, and 87 of every 100 flags it raises are real fraud. It missed both targets the project set itself: F1 0.85 and recall 0.85. Recall's upper interval just reaches 0.86, so the gate isn't hopeless, but on this evidence it isn't met.

Latency is comfortably inside budget. The model call takes 1.4 ms at the 95th percentile, measured on a single row with its features already computed.

<Callout title="What 1.4 ms measures">
  It's the model call alone, timed in-process. An API request also computes the
  window features, reads history from Redis and crosses the network, so its
  latency is higher. That end-to-end number hasn't been measured yet.
</Callout>

## Security

The scoring API checks an API key on every route except health and docs, and rate-limits requests. It loads pickled model files, which run code when opened; that's acceptable only because the files come from this repository's own build. The live demo on this site loads the LightGBM text model and plain JSON instead, so it never unpickles anything.

## What I'd do next

- Tune on a time-ordered validation block with the threshold chosen out of sample, so the headline no longer depends on the validation block also training the model.
- Rerun the evaluation from a clean clone and replace these numbers with that run.
- Measure end-to-end API latency under load, not just the model call.
- Move the tuning objective onto a time-ordered validation block, so tuning stops overestimating the model.
- Pick the threshold from an explicit cost of a missed fraud against a false alarm, rather than from a recall target.
